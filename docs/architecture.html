Architecture

The package keeps image semantics in Core and puts platform concerns at the edges. This lets the CPU reference implementation define behavior while Accelerate, Metal, Apple image bridges, Vision, the CLI, and the shared app consume that contract.

Dependency flow

The dependency direction is intentionally one-way. Core does not import Apple frameworks; the Apple facade owns backend selection and image conversion; Vision is an optional adapter; CLI and App are consumers.

Image data flow

  1. An Apple image bridge decodes an external image and applies orientation into the canonical upright coordinate space.
  2. The Core engine receives RGBA8 bytes, a positive PixelSize, ResizeOptions, and optional masks.
  3. The resize planner chooses width/height order and builds the energy plus mask adjustment for each current image.
  4. A backend finds and edits seams one at a time. Progress is emitted after committed edits, and cancellation is checked between edits.
  5. The Apple bridge encodes the resulting canonical image back to the requested image representation. The CLI then writes PNG, JPEG, or BMP.

Concurrency and memory

Core APIs are async and Sendable-oriented. The CPU implementation uses compact Float32 rows and parent/index buffers rather than a full cost matrix. Metal completion is awaited through a checked continuation and does not block the main actor. The app owns one resize task and cancels a previous task when a new resize starts.

Backend SPI types are internal-facing and marked with the Backend SPI. Ordinary clients should use SeamCarver or AppleSeamCarver, not implement the backend protocol directly.
